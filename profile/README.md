<h2>分配的本质是「固定对应关系」</h2>
<p>多店铺分配 IP，说起来是「一个店一个 IP」，做起来常出问题。原因不在数量，而在「对应关系是否被固定住」。如果对应关系靠人记、靠临时指定，用不了几周就会乱：某天赶时间随手换了一条，之后再也没换回来。</p>
<p>所以分配方案的核心不是分几条，而是怎么把关系固化下来。</p>

<h2>方案一：设备绑定</h2>
<p>最简单也最可靠。一台设备（或一个虚拟机、一个浏览器环境）固定使用一条出口，不做切换。隔离度最高，管理成本也最高。</p>
<p>适合主力店铺、账号数量不多的场景。店铺多了以后，设备成本会迅速上升，此时应考虑网关映射。</p>

<h2>方案二：网关映射</h2>
<p>在网关或路由器上配置「内网地址 → 公网出口」的固定映射。内网设备不需要单独配置，出口由网关决定。</p>
<p>优点是规则集中，改一处生效全局；可审计，谁走哪个出口一目了然。缺点是需要一台能做策略路由的设备，配置有一定门槛。</p>

<h3>映射表怎么维护</h3>
<p>一张表，四列：内网地址、对应店铺、出口地址、生效时间。四列都填，不要留空。留空的项就是将来出问题的地方。</p>
<h3>新增店铺怎么做</h3>
<p>先分配内网地址，再分配出口，然后更新映射表，最后验证。四步按顺序做，不要跳。跳过验证的，往往在几天后才发现出口配错。</p>

<h2>方案三：系统调度</h2>
<p>由业务系统按记录分配出口。适合规模较大、有开发能力的团队。核心是记录必须准确，且分配逻辑不能被随意绕过。</p>
<p>这类方案的常见问题是「有人手动绕过了系统」。一旦发生，记录与实际就不一致，后续所有判断都建立在错误的前提上。</p>

<h2>数量的确定</h2>
<p>按经营主体算，不按店铺算。同一主体下的多店可以共用一条出口；不同主体必须分开。在此基础上加一到两条备用。</p>
<p>不要按「未来可能开多少店」预留太多。闲置地址是纯成本，且会降低扩张时的谨慎度。</p>

<h2>台账与巡检</h2>
<p>台账三件事：记录对应关系、记录变更、记录异常。巡检两件事：核对实际出口是否与记录一致、核对设备是否仍在预期的网络下。</p>
<p>巡检频率建议每周一次。关键账号可以更频繁。发现漂移立即修正，并记录原因——原因往往指向流程漏洞。</p>

<h2>常见错误</h2>
<p>错误一，所有店铺共用一条出口，靠切换浏览器环境区分。出口同源，环境再独立也没用。</p>
<p>错误二，遇到验证就换 IP。频繁变更本身就是异常信号。</p>
<p>错误三，只做出口不做设备。同一设备登录多个主体，出口不同也会被关联。</p>
<p>错误四，没有台账。人一换，关系就断了。</p>

<h2>把「谁能改配置」也管起来</h2>
<p>分配方案能不能长期成立，最后取决于权限。如果每个人都能随手改映射、随手换出口，再好的方案也会在几周内被稀释。做法很简单：改配置只有一个人负责，改动必须更新台账并留下原因。这条规则看起来是管理问题，实际是技术问题——绝大多数「出口莫名变了」的案例，最后都能追溯到某次没有记录的改动。</p>
<h2>常见问答</h2>
<h3>一个店需要几条 IP</h3>
<p>一条足够。多给不会更安全，反而增加管理负担。</p>
<h3>同主体多店能共用吗</h3>
<p>可以。同一主体本来就是关联的，共用不新增风险。</p>
<h3>能临时借用别人的出口吗</h3>
<p>不建议。出口的稳定性是账号轨迹的一部分，借用会制造断点。</p>
<h3>怎么发现配错</h3>
<p>定期查询每台设备的实际出口，与台账比对。不一致即为漂移或配错。</p>
